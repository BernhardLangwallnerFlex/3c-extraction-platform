## 1. The KEDA fix — open, and now costing money every day

**Status:** interim fix in place, proper fix not started. Needs a spec.

### What is actually wrong

KEDA scales workers on `LLEN rq:queue:jobs-<product>`, but RQ removes a job from that list the
instant a worker picks it up. **A running job is indistinguishable from an empty queue**, so the
worker gets scaled in mid-job. Three consequences, discovered in this order:

1. **Retry churn.** RQ requeues and redoes the whole pipeline, OCR included. Measured at ~15
   kills per 244 job attempts over 30 days (~6%). Mostly invisible.
2. **Visible failures** when the kill lands on the last retry — this is the
   `Work-horse terminated unexpectedly; waitpid returned 15` the PO reports.
3. **Silent job loss — found 2026-08-18, and the reason this is now urgent.** A worker pops a
   job (`BLPOP` removes it from the list) and is SIGTERMed before it records the job as started.
   The job then exists only as an orphaned hash saying `queued`. RQ's retry budget never engages,
   because nothing knows the job needs requeuing. **The API reports `queued` forever and the user
   waits indefinitely.**

Evidence for (3): job `475c8f22` sat at `queued` for 12+ minutes while absent from the Redis list,
absent from every registry, with `worker_name = None`. Not eviction — 0 evicted keys, 578K used
of 272M.

Separately, **KEDA failed to scale up from zero** for those 12 minutes despite a queued job.
Forcing a replica started one instantly, so it was not an environment-capacity problem. That
second failure is not explained yet and is worth understanding before trusting scale-to-zero again.

### Interim fix currently running

**`minReplicas 1` on all six workers** (production and test). No scale-to-zero means no scale-in
means no lost jobs. Chosen deliberately as a holiday-stability measure, not as the answer.

**It costs roughly $300/month per replica at 4 CPU / 8 GiB — about $1,800/month across six.**
That is the clock on this topic. Revert with `az containerapp update -n <app> -g rg-3c-invoice
--min-replicas 0`.

### Suggested direction

Close the silent-loss hole in software rather than paying for standing replicas:

- A periodic sweep that finds jobs whose status is `queued` but which appear in no list, and
  re-pushes them. Cheap, testable, and it makes the failure self-healing instead of terminal.
- Then work out why the redis scaler would not scale up from zero, since that is what turned a
  short window into a 12-minute stall.
- With both, workers can scale to zero again and the $1,800/month goes away.

RQ 2.x has an intermediate-queue mechanism for reliable dequeue that may remove the window
entirely — worth checking whether it can be enabled here before writing custom recovery.

**Diagnostic recipe.** Connect to Redis with the app's `redis-url` secret and compare
`Queue.count` and `q.job_ids` against `Job.fetch(id).get_status()`. An orphan is a job whose
status is `queued` while it is in no list. Re-push with `q.enqueue_job(j)`.

## 2. 3C sign-off on the new API fields — happened out of order

**Status:** production now emits fields 3C has not formally signed off on.

`v20260818a` was promoted to production on 2026-08-18, ahead of sign-off, to avoid carrying the
large-format OOM risk through two unattended weeks. The trade was deliberate: an unsigned-off
additive field is recoverable, an OOM-killed worker on a real claim is not.

**What production now returns that it did not before:**

- `returncode` (100 = is a Beleg, 200 = readable but no Beleg, 300 = unreadable) and German
  `returncodeReasons` on every subdocument.
- `qualityFlags` — `VISION_DROPPED`, `SINGLE_ENGINE_OCR`.

All additive; nothing was removed or renamed. The consumer contract is in `vetcostcheck_api_doc.md`.

**Tell consumers to branch on `returncode`, never on `type == null`** — the prompt emits null
whenever the Belegart is unclear, so genuine-but-ambiguous Belege land there too.

**The asymmetry that governs every decision here:** a false 200 auto-cancels a legitimate claim;
a false 100 only reproduces today's behaviour, which a human already handles. Hence the floor is
fill-in-only, and the prompts carry *"Ein Beleg bleibt 100, auch wenn einzelne Felder nicht
ermittelbar sind."*

**Rollback if 3C objects:** `scripts/promote.sh <product> v20260813a --apply --force-rollback`.

## 3. Worker sizing — revisit once the KEDA fix lands

Workers went 2 CPU / 4 GiB → **4 CPU / 8 GiB** on 2026-08-18. Container Apps couples the two, so
8 GiB requires 4 CPU; the CPU doubling is a side effect, not a choice.

The render work bounded memory in code, but with the split site and analyze both bounded the
remaining ceiling is the **OCR phase** — Mistral renders each page under the 200 Mpx canvas
budget and its render loop alone measures 2.38 GB. Peak on the worst known document is 4.16 GB.

Capping OCR resolution was considered and rejected: unlike analyze's `detail: low` images, which
the API downsamples regardless, OCR resolution feeds text recognition directly, and a 48 Mpx cap
would change OCR input for 20 of 441 corpus files. If the cost of 4 CPU / 8 GiB ever bites, that
is the lever to re-examine — but it needs a quality check, not just a memory measurement.

**No CPU or memory setting exists anywhere in the repository** — not in `deploy.sh`, not in
`scripts/provision_product.sh`, not in `azure_deployment_plan.md`. The workers run on whatever
was set manually. Worth pinning in `provision_product.sh` so the next product does not inherit a
limit nobody chose.

## Reference — what shipped on 2026-08-18

**`v20260818a`, on test and production.** Three features, all merged to `main`:

| | |
|---|---|
| `returncode` + `returncodeReasons` | every subdocument classified; stops 3C opening a Vorgang for non-Belege |
| Content-policy fallback + `qualityFlags` | Azure's filter false-positives damage photos; falls back to text-only instead of failing |
| Render memory bound | fixes the large-format OOM |

**The render work in one line:** `core/rendering.py` picks dpi from a pixel budget and streams
pages through disk, so peak memory is canvas-plus-one-page. Peak on the failing document
5.1 GB → 4.16 GB.

**Two constants, both calibrated against measurement** — `CANVAS_BUDGET_PX = 200_000_000` and
`ANALYZE_BUDGET_PX = 32_000_000`. The plan's four amendments record what was measured and what it
overturned; **read them before changing either value**, because three successive calibrations
were wrong in ways that only measurement caught:

1. The canvas is a **bounding box** (`max(w) × sum(h)`), not the sum of page areas.
2. Calibrate on **subdocuments, not whole files** — production never renders a whole file except
   on the split-fallback path.
3. **The memory ceiling moves as you fix it** — split → analyze → OCR. Re-sample RSS by phase
   after any change; three predictions in a row were wrong.

**Regression gate:** 29 PDFs / 37 subdocuments across all three corpora, all `returncode` 100,
**zero `render_downscaled` events** — so every image was byte-identical to before.

**Azure OpenAI:** `gpt-5.4` capacity raised 50 → **500** (quota 21,000). At 50 a single 33-page
document exceeded the per-minute budget, which failed a real PO run. Note
`az cognitiveservices account deployment` has **no `update` subcommand** — it falls through to
help text and changes nothing. Use an ARM PATCH on `sku`.
